PATHMIND
Antigravity MVP Implementation Prompt Pack
UI/UX + Agent Architecture + Delivery + Git Workflow
Purpose: give Google Antigravity a disciplined sequence of implementation prompts for the PATHMIND MVP. The prompts are deliberately opinionated: premium product UI, real agent behavior, no fake integrations, no invented credentials, and no uncontrolled rewrites of the existing structure.
0. Non-Negotiable Rules for Antigravity
Treat the existing codebase as the source of truth. Inspect the current structure before modifying files.
Do not rewrite or replace working architecture unless a concrete incompatibility requires it. Prefer incremental changes.
Use Google ADK as the actual agent orchestration layer, not as a decorative dependency.
Use Gemini through the configured Google Gen AI / Vertex path already selected for the project.
Use shadcn/ui and KokonutUI for primitives and premium interaction patterns; use Motion/Framer Motion intentionally for transitions and state changes.
Avoid generic AI-dashboard aesthetics: no excessive gradients, floating glassmorphism everywhere, giant rounded cards, noisy glow effects, or fake terminal visuals.
The UI must feel like a premium learning product first and an AI product second.
Do not hardcode API keys, tokens, service-account JSON, credentials, URLs containing secrets, or fabricated integration IDs.
Whenever execution requires a credential or API key that is not already safely available in the environment, STOP at the relevant step and explicitly ask the developer for the exact credential or for permission to use the configured environment/secret store.
Never generate placeholder secrets such as 'YOUR_API_KEY', fake keys, fake service IDs, or hardcoded credentials just to make the app appear functional.
Use environment variables or the project's secure secret mechanism for all credentials. Validate presence at startup and fail clearly if required secrets are missing.
Never fabricate job, internship, certification, course, salary, or application links. Unavailable external data must be labeled as such.
Do not expose chain-of-thought. UI should show concise decision summaries, evidence, actions, confidence, and state transitions.
Every phase must end with: tests, type-check/build validation, a short change summary, and a list of any blockers or missing credentials.
Commit work in small logical units. Do not mix unrelated UI, backend, and infra changes in one giant commit.
1. UI/UX Direction
Visual direction: premium, editorial, intelligent, calm, and highly intentional. Think 'high-end learning OS' rather than 'AI SaaS admin panel'.
Typography: strong typographic hierarchy, restrained use of bold, generous whitespace, excellent line length, and readable body copy.
Layout: asymmetric compositions, large editorial sections, persistent context rail where useful, and focused single-primary-action screens.
Color: neutral foundation with one restrained accent and semantic colors only when they convey state. Avoid rainbow AI palettes.
Surfaces: use depth through spacing, borders, subtle shadows, and material hierarchy rather than blur-heavy glass cards.
Animation: use Motion for page transitions, progressive reveal, timeline movement, locked-to-unlocked states, evidence evaluation, and subtle microinteractions. Avoid animation for decoration.
KokonutUI: selectively use distinctive interaction components where they improve the experience. Do not install components merely to advertise the library.
shadcn/ui: use as the base component system and keep variants consistent.
Accessibility: keyboard navigation, visible focus, reduced-motion support, adequate contrast, semantic landmarks, and screen-reader labels.
Responsive behavior: desktop-first for the hackathon demo, but no broken tablet/mobile layouts.
The dashboard should communicate 'where I am, why I am here, what I need to do next' within seconds.

17. Git / Version-Control Strategy
Recommended branch model for a two-person hackathon team:
main — submission-ready, protected conceptually; only merge tested work.
develop — integration branch for completed feature work.
feature/* — individual implementation branches.
test/* — temporary integration or judge-flow verification branches when necessary.
hotfix/* — urgent fixes against main.
Recommended flow:
feature/profile-onboarding → PR → develop
feature/trajectory-brain → PR → develop
feature/progressive-roadmap → PR → develop
feature/memory → PR → develop
feature/career-engine → PR → develop
develop → test/hackathon-demo → validation
test/hackathon-demo → main only after final smoke test

22. Final Antigravity Execution Rule
Work phase-by-phase.

For each phase:
1. Inspect current code.
2. State exactly what you will change.
3. Implement the smallest coherent change.
4. Run validation.
5. Fix regressions caused by your changes.
6. Report files changed, tests run, and blockers.
7. Stop.

Do not automatically continue into the next phase.

When a credential is required:
STOP → ASK FOR THE CREDENTIAL → WAIT FOR CONFIGURATION → CONTINUE.

When requirements conflict:
prefer the existing codebase, the PATHMIND PRD, security, correctness, and minimal-change strategy in that order.

The goal is not maximum code.
The goal is a polished, credible, demonstrable MVP.
